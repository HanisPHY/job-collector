刷屏与埋没

三轮「设计 → 双向评审 → 实现」，把一份每天 3076 行、938 个链接的求职日报， 收敛成一屏 38 行、其中 30 行是真应届岗的阅读队列。这份报告记录循环里实际发生的事， 包括我作为编排者被数据驳回的三处判断。

/ 00先说结论：你现在拿到了什么

每天早上打开 logs/dashboard/latest.html，一个本地 HTML 文件， 零 JavaScript、零外部依赖、离线可开、跟随系统深色模式。默认展开的只有两段，共 38 行。

零丢弃是一条可断言的恒等式：六段相加 1018 == 当日去重后 1018 行。 中介不是被删掉，是被折叠到第 ⑥ 段并附上判据证据，你随时可以展开复核并改判。

两个需求怎么被满足的

需求 1（岗位变化 + 中介摆开）：变化面板按自然日对比，中介独立成段并标注判据； 「不能误伤岗位多的正常公司」由一条否决规则保证 —— 有自有 ATS board 的公司永不进中介段， Deloitte 52 条、Palantir 18 条、SpaceX 17 条全部留在正常区。

需求 2（大中公司排前面）：这个需求 dashboard 单靠面板解决不了， 所以做成了阅读队列 —— 一张 680 家公司的档案表（规模层级 tier 0-3、 知名度 prom 0-100、机构类型 kind），分段用离散判据，段内用 prom 排序。

/ 01循环怎么跑的

我编排流程并给每轮设计 steer；一个 PM & design subagent 出方案； 两个评估 subagent 从不同角度独立证伪；两人都放行才进实现。 评估者带着上一轮的完整上下文复用，所以它们记得自己提过什么、也会承认自己错在哪。

我的 steer

需求 2 本质是排序问题不是 dashboard 问题；需求 1 和 2 都需要同一张「公司档案表」； 现有离线名单只覆盖 8.8% 的公司，最可行的补法是一次性 LLM 富化。

PM 产出

680 家公司富化，51.6 秒 / $0.0139。首屏 140 行。声称对 60 家真实雇主零误伤。

我的 steer

把 LLM 从一次性 oracle 改成可累积的登记表：跑 3 遍取多数票 + 单调升级。

/ 02改变了结果的六个发现

01

阈值挂在了一个单调递增的计数器上

两个评估者独立收敛

「某公司岗位太多且 LLM 查无此人 → 判为中介」的阈值 ≥5，用的是跨天累计岗位数。 A 外推约 10 天后 300 家 tier-0 公司会被全部吞掉；B 实测现在 227 家只有 1 条，两个多月后陆续越线。 两人从完全不同的角度独立撞到同一处，基本可以确认为真。改成 7 天滑动窗口后， 在 0~6000 行/天的背景流量压测下恒定命中 8 家。

02

首屏排序排对了公司，排错了人

评估者 B · 整个循环里最有价值的一条

round2 的首屏按 prom≥85 切，35 行里只有 5 行是明确应届岗。 而被挡在折叠区的恰恰是 Micron 的 New College Grad、L3Harris 的 Associate SWE、BAE 的 Entry Level。 B 的原话：一个求职工具的独特价值在于告诉他那些他不会自己去查的公司 —— Amazon 和 Google 的招聘页他本来每天就刷。换成 30 行正则做分段依据后， 首屏 30 行里 30 行都是明确应届岗，零 LLM 成本。

03

响亮的崩溃被换成了安静的错误结论

评估者 A

round1 遇到未富化的公司会抛 KeyError —— 吵，但看得见。round2 修成「全函数、永不抛异常」， 却把「还没富化」和「LLM 说不认识」编码成了同一个状态，而后者正是判中介的触发态。 后果：富化晚一天，Amazon、Booz Allen、Micron 就出现在中介面板里；空表时连 Deloitte 都进。 实测修复后，空档案表下中介段从 168 行 10 家真实雇主变成 0 行 0 家。

04

两份评审报告的结论互相冲突，而它们自己不知道

编排者交叉比对

B 判 stage-2 富化不值得，理由是产出 100% 落在折叠区。但 B 在同一份报告里力推的新切法， 恰恰让 stage-2 回收的 GE Vernova 进了首屏 —— 例子还是 B 自己举的。 同时 A 的实验证明 stage-2 换 gpt-4o-mini batch 20 能便宜 12.4 倍。 两个前提同时被推翻，stage-2 留在 P0，日成本从 $0.244 降到 $0.07。B 后来正式撤回了判决。

05

规格自己和自己打架

两个评估者独立收敛（第三次）

施工规格写「相关性正则大小写敏感」，但规格里所有数字都是在不敏感下测出来的。 照字面实现，New Grad、Entry Level、Associate、Graduate、Intern 五个分支全部哑火，首屏从 28 行掉到 9 行，而且规格自己列的 12 行样例里有 8 行过不了。 两个评估者在最后一道放行时独立撞到同一处。

06

「知名度」分数只配用来排序，不配用来切分段

编排者提出 · PM 修正理由 · A 复现确认

LLM 给的 prom 分数三遍一致率只有 84.6%，4.4% 的公司会跨越阈值线 —— 而设计要把它冻结进缓存， 等于把抖动永久固化。排序对噪声不敏感（Amazon 92 还是 88 都排前面），阈值对噪声极敏感（84 和 85 天差地别）。 最终分段判据里一个 prom 阈值都没有。A 实测：只有 Truist 一行会在段 ①② 之间跳， 31 行里的 3%。

/ 05验收与遗留

验收 fixture：34 个 test 通过，2 条跳过（跳过的两条需要真调 LLM 跑全量富化）。 daily_report.py 逐字节未改 —— 你每天在看的 md 日报不受任何影响。 HTML 实测：原生 <details> 折叠、零 script / link / img / iframe 标签、深色模式在。 定时链路已接通：07:30 富化 → 08:00 日报 + dashboard。

收尾已完成：C 盘腾出空间后定时任务注册成功（Job - Enrich Companies， 每天 07:30，在日报前半小时）；586 家未分层公司已富化完毕 （1266 条档案，111 秒，$0.0411，0 丢行，stage-2 回收 40 家）。

收尾时真实数据暴露的一个设计缺口

富化后重跑验收，三条 fixture 变红。查下来 8/20 的语料在这期间从 1018 行涨到了 1674 行（采集器又跑了几轮，全部 unique_id 唯一，不是重复计数）， 于是段① 从 28 行涨到 61 行、首屏涨到 73 行 —— 超出了规格 §4.2 定的 30-50。

根因：cap=2 只约束单家公司，不约束当天总量，所以首屏行数会随采集量线性增长。 修法沿用 round 3 定下的原则（prom 只排序、不做阈值）：给默认展开的段加数量上限 （段① 35 行、段④ 12 行），溢出的进嵌套折叠。首屏回到 47 行，零丢弃不破。

另两条红的是点值型期望过期，不是代码错：中介检出从 8 家涨到 11 家， 因为语料变大后真的多了 3 家（Tech Consulting、Hire Feed、B4Corp 之类）。 关键的抗漂移性质仍然成立 —— 注入 0→6000 行背景流量，检出恒定 11 家。 三条 fixture 已按「断言不变性和结构性质，不写死点值」重写，36 个 test 全绿。

定时任务体检：13 个任务，两处真问题

接完线之后逐个核对了 Task Scheduler。配置全对（都指向 run_logged.bat、 触发器都启用、State 全是 Ready），采集任务也确实在跑，但查出两处会每天复现的故障。

② 更安静的一层：两个脚本都在读-改-写同一个 ats_registry.json，后写完的静默覆盖对方新发现的 board		 ①已根除 ②待一条提权命令

实跑时抓到一个当天早上就会炸的 bug

改完 .bat 后端到端实跑一次，dashboard.py 直接 UnicodeEncodeError —— 它往 stdout 打印段号 ①，而控制台默认是 cp1252。 之前一直没暴露，是因为 run_logged.bat 设了 PYTHONUTF8； 但双击 .bat 或任何不经过 wrapper 的调用都会挂。 已在 resolve_python.bat 里一并修掉，5 个脚本共享。 这条只有靠真的把脚本跑起来才会发现，读代码看不出来。

还需要你做两件事

一条提权命令（DDG_12 是旧的受保护任务，普通会话改不了， Access is denied）—— retime_ddg12.ps1 会先备份再把它挪到 13:00， 正好落在 ATS_12 结束（约 12:06）和 ATS_15 之间的空窗：

# PowerShell，以管理员身份运行
cd "D:\OneDrive\work\school\project\Job"

两分钟目视确认：a:visited（看过的岗位变淡）的 CSS 是 a:visited{color:var(--visited)} —— 纯颜色属性，浏览器一定会生效， 但那个颜色区分得够不够明显只有你能判断。

/ 06关于这个循环本身

最有效的不是任何单个 agent，是让两个评估者从不同角度独立工作。 三次出现两人独立撞到同一处缺陷 —— 累计计数器、正则矛盾、以及分母用错 —— 每一次都不需要再自证。 反过来，两人各自看不到的交叉矛盾（B 的两条建议互相冲突）只能由编排者比对发现。

第二有效的是强制先跑脚本再动笔。设计文档里每个断言背后都有一条实测， 所以评估者能逐条复现 —— A 第一轮复现了 13 条数字、全部通过，这让后续的分歧集中在真正的方法论上， 而不是「你这个数字是不是编的」。同样地，PM 三次用数据反对我，两次它是对的。

第三条是收尾阶段才补上的：再严密的评审也替代不了把东西真跑一遍。 三轮评审、13 条阻断项、36 条 fixture 都没抓到 dashboard.py 的 UnicodeEncodeError，因为所有人（包括我）都在已经设好 PYTHONUTF8 的环境里验证。它在第一次端到端跑 .bat 时立刻现形。 同样，首屏涨到 73 行、日报任务从未运行过、两个采集器争抢同一个 registry —— 全都是系统在真实时间里运行之后才暴露的，不是设计缺陷，是评审看不见的那一类问题。
