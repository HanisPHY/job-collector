# Round 1 评审 —— 评估者 B：用户价值与可持续性

> 评审对象：`dashboard_loop/round1_design.md`
> 视角：**假设评估者 A 查的数据全对**，这东西能不能真的解决用户的问题、能不能活得久。
> 本文所有新数字都是我自己在 2026-08-20 跑出来的，复现方式见文末附录。

## 结论：FAIL

**阻断项 6 条。** 判 FAIL 的直接理由是两条硬标准同时踩中：

1. **需求 1 的一半（「每天的岗位变化」）在 P0 里没有任何产物** —— 唯一回答它的 Panel ④
   被推到 P1，而方案自己在 §6.1 已经把两天的数据算出来了（中介占比 7.4% → 22.7%），
   并写下「这是需求 1 真正该看到的东西」。算出来了却不画，这是自相矛盾，不是取舍。
2. **P0-6「两级去重」会搞坏用户每天在看的 md 日报** —— 会让已有的 count-mismatch
   告警变成结构性每日误报，并静默删掉 md 里的岗位行。

除此之外还有一条会随时间恶化的判定漂移（阻断项 B4），它长期违反用户唯一说出口的硬约束
「不能排除掉岗位多的正常公司」。

**但请注意：FAIL 的是实施切分和几个具体机制，不是方案的骨架。**
公司档案表（tier / kind 正交）+ cap-2 压缩这条主干我认为是对的，而且是解得最漂亮的一处。
第 6 节列了我认为做对的部分；第 5 节给了一个我实测过的、能拿到 97% 收益的更简版本。

## 1. 需求覆盖度逐条对照

### 1.1 需求 1 上半句「每天的岗位变化」—— ❌ 未满足

| 拆解 | 方案的回答 | 判定 |
|---|---|---|
| 「变化」是什么？ | **全文没有定义**。Panel ④ 只说「近 N 天按 lane 堆叠 + 中介占比折线」 | 含糊过去了 |
| 只有 2 天数据时怎么办 | §7.4 表格写 Panel ④「画 2 根柱，坑位留空，不告警」；P1-1 又写「只有 2 天数据，画出来没信息量，等 ≥7 天」 | **两处自相矛盾**，最终结果是 P0 不做 |
| P0 里还剩什么能回答「变化」 | Panel ②（今日漏斗）是纯当日快照；Panel ①③ 也是当日 | **零** |

方案在 §6.1 已经把两天的 lane 分布都算出来了：

```
8/19  A1 55 / A2 47 / B 111 / C 17     中介占比 7.4%
8/20  A1 172 / A2 156 / B 301 / C 185  中介占比 22.7%
```

这 8 个数 + 1 个比值就已经是一个完整可用的「变化」面板，它不需要 7 天历史。
用户想知道的「今天跟昨天比多了什么」，在 2 天数据下最有信息量的形式恰恰不是折线图
（2 个点画成图，信息密度反而更低），而是一张 4 行对照表 + 两个衍生量：

- 每个 lane 的 今日 / 昨日 / Δ
- 中介占比 7.4% → 22.7%（这一个数就解释了「今天为什么暴涨」）
- **今天第一次出现的公司数 / 昨天有今天没有的公司数** —— 方案完全没提这个维度，
  但它最贴近用户对「岗位变化」的直觉（实测 8/20 的 554 家 newgrad 公司里
  只有 12 家在 8/19 出现过）

「变化」还有第三种含义方案没有回答：**消失的岗位**。`date_recorded` 是首次收录时间，
岗位一旦入库就永远在 CSV 里，LinkedIn 下架了也不会反映。方案不必现在实现，
但必须写明「本方案不追踪岗位消失，dashboard 上的『变化』= 新增侧的变化」，
否则用户会以为看到的是净变化。

### 1.2 需求 1 下半句「刷屏中介单独摆开」—— ✅ 满足，形态也对

「摆开」被实现成两处，这个组合是对的：

- Panel ① 队列里 Lane C 作为**最后一段**存在（不是删除，不是藏到另一页）
- Panel ③ 一张 62 行证据表：`公司 / 今日 / 累计 / LLM kind / 触发信号`

**用户想复核「这家是不是被误判了」时方便吗？** 部分方便：证据串
（`unknown+vol39`、`stack=8`、`LLM:aggregator`）是可解释的，比 req1 的
「只摆证据不打标签」进了一大步。**但翻案闭环是断的**，见 N-1。

### 1.3 需求 2「大中公司先看到」—— ✅ 满足，是本方案最强的部分

- 排序有了：tier 3 → 2 → 其他，§6.2 实测 TOP 30 里没有一条刷屏。
- 压缩有了：965 → 140，6.9 倍。cap-2 这个杠杆选得对 —— 纯排序下 Deloitte 27 条
  会吃掉整个首屏。

### 1.4 「140 行是不是还是太多」—— 方案正面承认了，但答案不完整

方案 §6.2 第 3 点主动写了「140 行仍然偏多」，这份诚实我认可。但把解法
（岗位相关性过滤）推给 P1-3 之后，**P0 就没有回答「用户每天能看多少条」**。

| 对照 | 量级 | 说明 |
|---|---|---|
| 现在的 md 日报（8/20 实测） | **3076 行 / 543 个公司小节 / 938 个链接** | 用户现在实际在看的东西 |
| 方案 Panel ① Lane A1 cap2 | 140 行 | 提升 6.7 倍 |
| 「早上 5 分钟」的物理上限 | 约 50–60 条（每条 5 秒扫标题） | |

**140 相对 3076 是巨大进步，我不因为「140 > 50」判 FAIL。**
但 P0 必须给出「首屏默认展开多少」的答案，而不是把四个 lane 全铺开 —— 见 N-3。

## 2. 阻断项（blocking）

### B1. 「每天的岗位变化」在 P0 里没有产物

**不改会怎样**：用户提的两个需求，交付的只有一个半。他明确说「dashboard 能清楚看到
每天的岗位变化」，而 P0 交付的是一个纯当日快照的 dashboard。

**必须改成**：Panel ④ 降级为 **Panel ②′「今日 vs 昨日」进 P0**。最小形态（2 天即可用）：

```
              昨日    今日      Δ
A1 大厂        55     172    +117
A2 大中        47     156    +109
B  其他       111     301    +190
C  中介/刷屏   17     185    +168     占比 7.4% → 22.7%  ▲
今天第一次出现的公司：542 / 554
```

等积累到 ≥7 天再升级成堆叠柱 + 折线，那时只是渲染层替换，不影响判定层。

### B2. 队列的时间窗漏掉每天约 2/3 的岗位，且没有已读状态

**这是我认为最关键的一条**，编排者的直觉方向是对的，但真实破绽比「第二天重看同样
140 行」更严重。

实测 8/20 的 `date_recorded` 逐小时分布（newgrad）：

```
00时 34   01时 126  02时 83   03时 74   04时 68   05时 108  06时 101  07时 78
--------------- 日报定时任务在 08:00 生成，窗口到此为止 ---------------
08时 117  09时 147  10时 28  …（数据截止 10 时）
```

`daily_report.py` 用 `date.today()` 过滤 `date_recorded[:10]`，Task Scheduler 在 **08:00** 跑。所以：

- D 日 08:00 的报告 = D 日 00:00–08:00 的岗位（实测 672 条）
- D 日 08:00–23:59 的岗位（截止 10 时就已有 292 条，按小时速率外推全天 1200+ 条）
  **不进 D 日的报告，也不进 D+1 日的报告 —— 它们永远不会出现在任何一份第 1 节里。**

Panel ① 完全继承这个窗口（`_verify_queue.py`：`today=[r for r in rows if r['_day']==DAY]`）。
**不改会怎样**：用户每天早上看到的「今日阅读队列」，系统性地只覆盖当天产出的三分之一，
缺的还是白天时段（新鲜度最高的那部分）。这不是显示 bug，是队列在真实使用节奏下不成立。

**已读/已投的现状**：

- `applied` 列全库 100% 为空（我复核了三个 CSV，非空 0 行）。
- 现在的 md 日报**至少还过滤了** `applied` 非空的行（`render_todo` 的 `unapplied`）。
  方案的 Panel ① **完全没提 applied**，连这个钩子都丢了 —— 相对现状是**功能回退**。
- P1-4 承认「该列 100% 为空，先要有写入路径」，但 P0 没给任何替代。

**一个改动同时解决这两件事：水位线（watermark）**

把队列窗口从「自然日」改成「**上次报告生成之后新增的岗位**」：

```
logs/last_report.json   {"cutoff": "2026-08-20 08:00:12"}
Panel ① 的行 = date_recorded > cutoff
生成成功后把 cutoff 推进到本次生成时间
```

- 不再漏：08:00–24:00 的岗位下次生成时一定会出现。
- 不再重：看过的窗口不会第二次出现（这就是「已读」的 80% 解）。
- 零新依赖，一个时间戳文件，不碰 md 日报（md 继续按自然日，视觉零变化）。
- 手动重跑要能覆盖：加 `--since` / `--no-advance`，重跑时不推进水位线。

**再叠一层几乎零成本的「已点过」**：岗位链接用 `<a>`，CSS 给 `a:visited` 一个变淡的颜色。
浏览器天然按 URL 记住，跨天、跨重新生成都有效，零 JS、零状态文件、离线可用。
限制：浏览器出于隐私只允许改 `:visited` 的颜色类属性（改不了
`text-decoration` / `opacity`），这构成对「状态色必须配图标+文字」约定的一次
**故意例外**，需要在文档里写明（见第 4 节）。

真正的 `applied` 写入路径（`mark_applied.py <unique_id>…`）可以留 P1，
但**水位线 + `:visited` 必须进 P0**。

### B3. P0-6 的两级去重会搞坏现有 md 日报

机制（我读了 `daily_report.py` 确认）：

1. `build_alerts()` 有一条自检：`reported = sum(new_jobs from runs.jsonl)`，
   `if tracked and reported != len(jobs_today)` → 告警。把 `(公司, 标题)` 去重加进共用的
   `dedup()`，`len(jobs_today)` 从 938 掉到 814，而 runs.jsonl 报的仍是采集器写入的原始条数
   → **这条告警从此每天必报**。（它现在已经在报 `778 vs 938` 了，再叠一层会让它彻底
   失去信号价值。）
2. `render_todo()` 直接消费 `dedup()` 的输出。两级去重后，Deloitte 那 14 条同名
   `Audit - Valuation & Analytics - AI Specialist` 会**从 md 里静默消失 13 条** ——
   它们是 13 个不同的 LinkedIn URL（不同 req / 不同地点），用户现在能看到，改完就看不到了，
   而且报告不会告诉他被删了。

**不改会怎样**：用户每天在看的那份 md 的数字和内容都变了，变化方向是「少了东西」，
这正是「不能回退」要防的事。

**必须改成**：`(公司,标题)` 去重**只作用于 dashboard 的 Panel ①**，不进共用 `dedup()`；
自检告警的分母永远用 uid 去重后的条数；即便在 Panel ① 里，同标题也应折叠成
`+13 条相同标题` 而不是删除。

### B4. 「量大 + 查无此人」用的是累计岗位数，会随时间不断误伤真实雇主

**证据**：`_verify_queue.py` 里 `n=len(allg[c])` 是该公司在**全库所有日期**的岗位总数，
`susp = kind=='unknown' and tier==0 and n>=5`。阈值挂在一个**单调递增**的计数器上，
而阈值固定为 5。

方案 §4.3 的阈值扫描（≥5 时 0 误伤）**只在一个 2 天语料上成立**。我实测当前
tier0+unknown 的 300 家公司的累计岗位数分布：

```
1 条: 227 家   2 条: 45   3 条: 11   4 条: 8   5 条: 3   6 条: 1   8 条: 2   9 条: 3
当前累计 >=5 的: 9 家    >=4: 17 家    >=3: 28 家    >=2: 73 家
```

227 家现在只有 1 条的 tier0 公司，只要以后每两周再发 1 个岗位，**两个多月后全部越过 5**，
然后被自动打上中介标签摆进 Lane C。方案 §4.3 的核心论证是「量本身从来不是判据，
量大只在 LLM 从没听说过它时才是判据」—— 但 LLM 没听说过的小公司**恰恰是绝大多数
真实小雇主**（方案 §7.2 自己列了 Fionics / Netic / Muon Space / Confido 这些
「保守但正确」的 unknown）。时间一长，这条规则会把它们一个个吞掉。

**不改会怎样**：静默地、逐步地违反用户唯一说出口的硬约束。用户不会知道某家公司
哪天开始不再出现在正常层里。

**必须改成**：换成**滑动窗口**（近 7 天条数 ≥5，或单日条数 ≥5）。关键点：
**在当前 2 天语料上，7 天窗口与累计计数完全等价**（语料本身只有 2 天），
所以这个改动**不损失任何已验证的准确率**，纯粹是拆掉一颗定时炸弹。
再加一个监控项「被自动判为中介的公司数 / 总公司数」（照抄方案已有的 tier3 膨胀监控）。

### B5. 失败隔离没有落到实施上：没网 / key 失效时 dashboard 会挂

§7.5 写了「富化失败 → 该公司 tier 0 落 Lane B，**不阻塞报告生成**」——
方向对，但 P0 的三处具体设计与之矛盾：

1. **P0-9「`run_daily_report.bat` 在日报前调 `enrich_companies.py`」**。
   批处理里前一条命令崩了不会中断后续，这点没问题；**但它挂起就完了** ——
   OpenAI 连接卡住、代理无响应、DNS 超时，没有任何超时或熔断，整条日报任务停在那儿，
   `run_logged.bat` 也写不出 `run_end`，第二天报告显示 `crashed`。这是定时任务，
   用户不一定马上发现。
   → **必须给 enrich 一个整体墙钟上限**（例如 180 s，实测全量 680 家只要 51.6 s），
   超时就放弃本次富化直接往下走。更稳妥的做法见 §5.4：**把富化从日报任务里拿出来
   单独一个任务**，日报永远只读缓存。
2. **参考实现 `_verify_queue.py` 里 `v=P[c]` 是直接下标**，profiles 里没有这家公司就
   `KeyError`。富化失败的那天正好会出现「CSV 里有、profiles 里没有」的公司。
   → `resolve()` 必须是**全函数**：缺失 = `{kind:'unknown', tier:0}`，永不抛异常。
   这条要写进 P0-5 的回归 fixture（造一个 profiles 缺失的用例）。
3. **`company_profiles.json` 的写入必须原子**（`os.replace`）。它在 OneDrive 同步树里，
   SCHEDULING.md 已经专门警告过 OneDrive 会短暂锁文件、与原子替换打架。
   半截写坏的 profiles.json 会让**之后每一天**的 dashboard 都生成失败。
   → 原子写 + 读取时 JSON 解析失败降级为「当作空档案表」而不是崩溃。

**「必须联网才能生成 dashboard 吗？」** 按修正后的设计：不必须。富化是**写缓存**的一步，
渲染只读缓存；req1「离线可开」针对的是**打开** HTML（纯内联，没问题）。
但方案没说清的一点：**离线时仍应能生成一份 dashboard**（新公司全部 tier 0 落 Lane B），
并在面板上显式标注「今日富化失败，N 家新公司未分层」。静默降级比报错更危险 ——
用户会以为今天真的没有大厂岗位。

### B6. P0-1 重构缺「md 日报零变化」的验收标准

P0-1 要动 `daily_report.py` 约 150 行（`collect_report` / `build_alerts` 返回结构化 /
`load_jobs` 改成一次读全部）。方案的 P0 验收标准 **5 条全是关于新功能的**
（fixture FP=0、Lane A1 行数区间、Lane C 条数区间、富化耗时花费、6 家公司在 Lane A），
**没有一条保护现有的 md**。

**不改会怎样**：用户每天唯一在看的产物，被一次「机械为主」的重构悄悄改掉格式或数字，
且没有任何自动化手段能发现。`build_alerts()` 返回值从 `list[str]` 改成 `list[dict]`
会同时影响 `render()` 和 `main()` 里的控制台打印（`alert.replace('**','')`），
漏改任何一处都是行为变化。

**必须加一条验收**：

```
python daily_report.py --date 2026-08-19 --no-prune  →  与已归档的 logs/daily/2026-08-19.md 逐字节相同
python daily_report.py --date 2026-08-20 --no-prune  →  与已归档的 logs/daily/2026-08-20.md 逐字节相同
（重构前先把这两份 md 拷成 fixture；重构时输出到临时路径做 diff，不要覆盖原文件）
```

这两份 md 现在就在 `logs/daily/`（51 KB / 140 KB），是现成的黄金样本。
**如果按第 5 节的简化方案走，P0-1 整个可以不做，这条自动消失。**

## 3. 非阻断项（可进 P1）

**N-1. Panel ③ 的「勾选框 → 生成 override 片段」在零 JS 下不成立。**
纯 HTML 的 checkbox 勾了不会改变 `<textarea>` 的内容，页面也没有提交目标。
§5.3 描述的「一键翻案」实际是：用户勾一堆没有任何作用的框 → 再手动去编辑器里敲 JSON。
**建议**：去掉 checkbox（会误导人的死 UI），改成每行直接显示**可复制的 override 键名**
（`norm()` 后的键 —— 用户没法自己猜出 `Infosoft, Inc.` → `infosoft`），
表格下方给一段包含全部 62 行、默认全注释掉的模板，删注释即可。
若允许 ~15 行内联 JS（req1「零 JS」的原文语境是「不引 CDN 的 Chart.js」
「悬停用 SVG `<title>` 而不是 JS tooltip」，不是禁止内联脚本），
checkbox → textarea 是可行的，但这需要编排者/用户明确松绑约定。

**N-2. 人工覆盖的工作流步数。** 现在是：打开 dashboard → 记住公司名 → 打开
`company_overrides.json` → 猜/查 `norm()` 键 → 写 JSON → 重跑 `daily_report.py`
→ 重新打开 HTML，**6 步**；加上 N-1 的键名显示后是 5 步。
「下次富化会不会覆盖回去」这点方案回答得很好：override 只读不写、决议顺序第 1 位、
LLM 全量重跑冲不掉（§7.3），这部分设计是对的。
**建议 P1**：`python override.py add "Infosoft, Inc." --kind staffing` 一行命令，
自己算 `norm()` 键、自己合并 JSON、自己重跑日报。

**N-3. 各 Lane 的默认折叠状态没有定义。** 方案只说 Lane B 默认折叠成一行，
A1 / A2 / C 没说。若 A2 默认展开，首屏实际是 140 + 149 = **289 行**，
「140 行第一屏」就不成立了。**必须在实施前定死**。建议：A1 展开（140）、
A2 折叠（一行「大中公司 149 条，展开」）、B 折叠、C 折叠，用 `<details>` 元素，
零 JS、浏览器原生、离线可用。

**N-4. 配色约定的三处未对齐**（详见第 4 节）。

**N-5. `company_profiles.json` 的增长与 OneDrive。**
实测：sample 文件 680 家 / 94 KB / 平均 118 字节每家。方案 §7.1 假设
「每日增量新公司 100 家」是**没有依据的**。我实测 8/20 的逐小时新公司数是
`14, 56, 45, 41, 50, 57, 61, 47, 71, 87, 13`（11 小时内 542 家新公司，
**曲线没有任何收敛迹象**）。按 ~50 家/小时外推，稳态可能是 **500–1200 家/天**：

| | 方案假设 | 实测外推 |
|---|---|---|
| 新公司/天 | 100 | 500–1200 |
| 富化成本/天 | $0.002 | $0.010–$0.025 |
| profiles.json 一年后 | ~4 MB | **21–50 MB** |

成本仍然离 `LLM_DAILY_COST_ALERT_USD = 0.50` 差两个数量级，
**不会天天触发告警，这一点方案是安全的**；首次全量 $0.0139 也不会。
但一个每天被整体重写、几十 MB、放在 OneDrive 同步树里的 JSON 是真实的可持续性问题。
**建议 P1**：(a) 支持 `JOB_PROFILE_PATH` 环境变量把它挪出 OneDrive（照抄
`JOB_LOG_ROOT` 的现成模式）；(b) 超过 90 天没再出现的 tier0/unknown 公司可以丢弃
（下次遇到再花 $0.00002 重问一次）。

**N-6. 档案永不复评。** 一家公司被判 tier 0 就永远 tier 0，没有 TTL，也没有
「模型升级后重问」的路径（只有手工全量重跑）。$0.014 一次的价格下不值得设计复杂机制，
加个 `--refresh-unknown`（只重问 kind=unknown 的）就够了。

**N-7. 没有稳定入口。** 产物是 `logs/daily/<day>.html`，用户每天要进两层目录找当天的文件。
**建议**：同时写一份 `dashboard.html` 到仓库根目录（或 `logs/daily/latest.html`），
桌面放个快捷方式，双击永远打开最新的。一行 `shutil.copyfile`。

**N-8. 缺一个 hero 数字。** req1 可视化约定第一条是「头条数字用 stat tile / hero」，
六个面板里没有任何 hero。「今天必看 140 条（昨天 35）」是这份 dashboard 最该有的
第一个像素，成本几乎为零。

**N-9. LLM 花费的归属会混进 md 日报。** 富化如果在 `run_daily_report` 这个 run_id 下写
`run_summary`，`collect_llm_usage()` 会把它并进当天总花费，md 日报第 1 节的
「LLM spend」会从 $0.0265 变成 $0.04 左右而不解释原因。建议富化的 summary 带一个
可区分的 `script` 名，md 里按脚本分行显示。
P0-3（把 `gpt-4o-mini` 加进 `MODEL_PRICING`）方案已经识别到了，**这一条抓得很好**
—— 不加的话「unpriced model」告警会每天触发。

**N-10. 定时任务改动量：极小，这一条方案是对的。**
12 个任务全部指向 `run_logged.bat <collector>`，动作层不用碰，只需改
`run_daily_report.bat` 两行（或按 §5.4 新增一个任务）。
**不需要提权，不需要重跑 `repoint_scheduled_tasks.ps1`。**

## 5. 复杂度是否配得上收益 —— 一个我实测过的更简版本

**判断：骨架不过头，实施切分过头了。**
「公司档案表 + LLM 富化」这一件事本身极其划算（$0.0139 一次、51.6 秒、
覆盖率从 9% 跳到 100% 有结论）。过头的是**围绕它堆的东西**：5 条信号里 3 条几乎不产生
增量、6 个面板里 2 个和现有 md 重复、以及一个高风险的 `daily_report.py` 重构。

### 5.1 实测消融：S2 / S3 / S4 三条信号可以整条删掉

我用方案自己的参考实现跑了消融（8/20，同一份 profiles）：

```
全部 5 条信号  (S1+S2+S3+S4+S5)  →  中介层 69 家 / 当日 185 条
只留 S1 + S5                     →  中介层 67 家 / 当日 179 条   （保留 96.8%）

只被 S2/S3/S4 独占命中的公司，全库只有 2 家：
   Capgemini        累计 6 条 / 当日 3 条   LLM 判 employer  靠 S4(stack=3)
   Infosoft, Inc.   累计 3 条 / 当日 3 条   LLM 判 unknown   靠 S4(stack=3)
S2（转贴 " at X"）独占命中：0 家     S3（标题以 Jobs 结尾）独占命中：0 家
```

也就是说：**S2 抓的 Jack & Jill 已被 S1 抓到，S3 抓的 Surge Software 已被 S5 抓到**，
这两条信号的边际贡献精确为零。S4（技术栈发散度，需要维护一张 23 词的技术栈表，
是全套里最脆的一条）只换来 6 条岗位（3.2%），而方案自己也承认 Capgemini 那一次是
「歪打正着」。

**判定层从 5 步降到 4 步**：`O1 覆盖 > S1 LLM kind > V1 ATS 否决 > S5 窗口内量大+查无此人`。
方案 §4.2 关于「V1 排在 S1 之后」的实测结论（Jobgether）依然成立，原样保留。

### 5.2 不要重构 `daily_report.py`

方案主张「不拆成两个**文件**」，理由是用户不该每天开两个东西 —— **这个结论我完全同意**。
但它被错误地推导成了「所以要重构 `daily_report.py` 让两个渲染器共享 `collect_report`」。
**用户看到的文件数**和**代码怎么组织**是两回事：md 和 html 本来就是两个文件，
用户只是不再需要看 md 而已。

更简单的做法：新建 `dashboard.py`，
`from daily_report import load_jobs, dedup, day_of`（这三个函数现在就是可导入的纯函数），
自己读 profiles + overrides，自己渲染 HTML。

- `daily_report.py` **一行不改**（除 P0-3 的 4 行价格表）→ 阻断项 B3、B6 直接消失，
  用户每天在看的 md 零风险。
- 省掉 P0-1 的 ~150 行高风险改动。
- 代价：健康/告警/花费三块逻辑无法复用到 HTML —— 但按 5.3 这三块本来就不该进 P0 的 HTML。

### 5.3 面板从 6 个降到 3 个

| 面板 | 去留 | 理由 |
|---|---|---|
| ① 阅读队列 | **留** | 需求 2 的全部产物 |
| ②′ 今日 vs 昨日（4 lane 对照 + 中介占比 + 新公司数） | **留**（B1 要求的新形态） | 需求 1 上半句 |
| ③ 中介证据表 | **留** | 需求 1 下半句 |
| ② 漏斗 | 可留可不留 | 是个好东西（让人敢信折叠），但信息量被 ②′ 覆盖大半 |
| ⑤ 采集器健康 | **P1** | md 日报第 2、3 节已经有了，且用户仍在看 md。重复实现一套状态色+图标是纯成本 |
| ⑥ 告警 + LLM 花费 | **P1** | 同上 |

### 5.4 富化不要塞进日报任务

新建一个独立的 Task Scheduler 任务 `run_logged.bat run_enrich_companies`，每天跑一次
（排在日报之前，例如 07:30）。日报/dashboard **只读缓存**。这样富化挂了、超时了、
没网了，dashboard 照常生成（新公司落 Lane B），唯一后果是一行提示
「N 家新公司今日未分层」。B5 的三个隐患一次性解决。
新增任务不需要管理员权限（SCHEDULING.md 明确说了 Register 新任务不用提权）。

### 5.5 简化版 P0 汇总

| # | 任务 | 规模 |
|---|---|---|
| 1 | `enrich_companies.py`（按 name 回填、原子写、整体超时、`--refresh-unknown`） | ~150 行新增 |
| 2 | 直接用 `dashboard_loop/company_profiles.sample.json` 作初始缓存 | 0（省掉首次 $0.0139） |
| 3 | `company_lane.py`：`resolve()` 4 步决议，全函数不抛异常，S5 改 7 天窗口 | ~80 行新增 |
| 4 | `company_overrides.json` 读取 | ~20 行 |
| 5 | `dashboard.py`：3 个面板 + 水位线 + `:visited` + `<details>` 折叠 | ~250 行新增 |
| 6 | `gpt-4o-mini` 进 `MODEL_PRICING` | 4 行改动 |
| 7 | 回归 fixture（60 真实雇主 / 59 中介 / 1 个 profiles 缺失用例） | ~80 行 |
| 8 | 新增一个 Task Scheduler 任务跑富化 | 3 行 PowerShell |

**约 580 行新增 + 4 行改动，零行现有分析/渲染代码被改。**
对比原方案的 ~950 行新增 + ~165 行改在用户每天依赖的文件里。
收益：需求 2 完全满足（一样的 140 行队列）、需求 1 的中介判定保留 96.8%、
需求 1 的「变化」反而**从没有变成有**。

## 6. 方案里我认为做对的部分（不是客套，这几条应当原样保留）

1. **真的花钱做了实测，而且实测推翻了自己的假设。** gpt-3.5-turbo 对两家编造的公司
   2/2 编造答案并给 conf 0.9 —— 这个探针设计得好，而且结论直接改变了模型选择。
   没有这一步，这套系统会带着一个会瞎编的判定层上线。
2. **第一版 prompt 把 Deloitte / Booz Allen / Leidos / L3Harris 全判成 staffing，
   然后如实写了出来。** 正是用户点名不能误伤的公司。把失败过程写进设计文档，
   比只报「0 误伤」有价值得多，也让「改 prompt 必须重跑 fixture」这条约束有了
   不可辩驳的理由。
3. **`tier` 与 `kind` 正交** —— 「规模大不等于该看」。TCS = tier 3 + outsourcing、
   Robert Half = tier 3 + staffing 把设计意图讲得非常清楚。这是整个方案最聪明的一处，
   它同时让「按量打标签」变安全了。
4. **拒绝把 conf 当阈值**，理由是实测 conf 是离散编码不是概率（0.2 ⟺ unknown）。
   用 `kind=="unknown" and tier==0` 当「不知道」的判据是对的，少一个会漂移的魔法数字。
5. **cap-2 而不是纯排序。** 「排序只决定顺序，cap 才是『看不过来』的解药」——
   这是对用户需求的正确翻译，也是 965 → 140 的关键。
6. **否决位 V1 排在 S1 之后**，并用 Jobgether（聚合站但有自己的 Ashby board）
   这个真实反例证明顺序不能反。CONTEXT_BRIEF 里「ATS 直连 = 必定真实雇主」
   被正确地降级了。
7. **「标题重复率」的反直觉结论**（Deloitte 87% / Jack & Jill 9%）。这条如果不测，
   几乎所有人都会把它当中介信号用，然后精确地误伤 Deloitte。
   把它重新定位成「压缩机会而非中介信号」是正确的转化。
8. **明确反对 CONTEXT_BRIEF 的「跨天持续性」信号**，理由是 8/19 是残缺日
   （newgrad 只有 101 条），拿它当基线会把 97.8% 的公司判成「突发」。
   敢于推翻上游简报里的既有结论并给出数据，这是对的。
9. **LLM 批次少返回行导致按位置对齐整体错位**这个失败模式被真实撞到并修掉
   （改成按 name 回填）。这是最危险的一类静默错误，被抓到了。
10. **§9 的 11 条「放弃的方案」全部带数据。** 尤其 9.10（岗位级打分年成本 $9
    vs 公司级 $0.7，且岗位级无法缓存）和 9.8（Epic Systems vs Epic Placements
    不能前缀合并），这些是真正省下未来返工的判断。
11. **定位了 `company_type` 39% 虚高的根因**：旧分类器 prompt 里写着
    「When in doubt, prefer classifying well-known large companies as 独角兽/上市公司/Big Tech」。
    找到根因并说明新 prompt 用的是相反指令，比单纯说「这个字段没用」强得多。
12. **P0-3 提前发现 `gpt-4o-mini` 不在 `MODEL_PRICING` 里**。不加的话
    「unpriced model」告警会每天触发，属于上线后要查半天的噪音。
