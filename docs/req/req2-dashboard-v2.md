## 1. 目标与需求

用户原话：

> 总的目标就是，我想要看**过去 N 天**的岗位变化和分段后的岗位。
> 我可能会想看过去 N 天的分段然后**从里面挑 job 来投递**。

| # | 需求 | 现状 | 已定的决策 |
|---|---|---|---|
| R1 | 趋势图天数可调 | 写死 `TREND_DAYS = 7` | **N 从 1 / 3 / 7 / 14 / 30 里选**，不是任意输入 |
| R2 | **分段支持 N 天窗口** | 只有单个自然日 | 同上。**本文重点** |
| R3 | 点击堆叠条 → 跳到对应分段 | HTML 里 `id=` 属性数量为 **0**，没有任何锚点 | 加锚点 + 十几行 JS |
| R4 | 前后端拆分 | 583 行 Python 拼 HTML 字符串，CSS 是 Python 字符串常量 | 真 `.html` / `.css` / `.js` 文件 |

**R2 是核心。** 用户说明了用途：从 N 天窗口里挑岗位投递。
这意味着窗口视图不是「看统计」，是**工作台** —— 排序、分段、日期列都要为
「一条条看过去、挑出来」服务。

### 明确不做：已投 / 已忽略

**用户已决定本轮不做，不要自作主张加回来。**

相关事实留在这里供以后判断：CSV 的 `applied` 列存在但**全库 0/2491 非空，从没被用过**；
窗口视图下同一条岗位会连续 N 天出现在眼前，没有已读/已投标记时这一点会比单日视图明显。
目前唯一的「看过」线索是 `a:visited`（浏览器状态，换浏览器或清缓存就丢）
和水位线驱动的「● 新」标记（只表示「上次生成报告之后新增」，不表示「你处理过」）。

真要做的时候有一道坎先解决：页面是 `file://` 双击打开的静态 HTML，
**JS 不能直接写本地文件**，所以点击状态怎么落盘需要先做技术验证（见第 6 节的表）。

### 为什么最后选了预设而不是任意输入

一句话记录，免得下一轮又推翻一遍：

一开始我（编排者）说「预设方案便宜好几倍」，**这个说法是错的**，因为它把两个独立的轴
混成了一个选择 —— 「谁来筛 N」和「渲染写在哪」。预设省下的钱恰恰就是 R4 的钱，
而 R4 是独立提出的需求（理由是维护性，跟 N 天无关）。
**一旦做了 R4，浏览器里筛 N 几乎是免费附赠的。**

最终选预设，理由不是省钱，是：
- 固定 5 档让**数据可以按档分块预生成**，首屏只加载今天那一块（见 5.5）
- 5 档覆盖了真实使用场景，任意输入没有额外价值

### 证据标准

**你可以推翻上面任何一条已定结论，但必须先跑脚本给出反证。只讲道理不算。**

理由不是"这些结论神圣不可侵犯"——上一轮它们本身就被修正过好几次，
每一次都是拿数据推翻的。规则约束的是**货币种类**，不是允不允许交易。

一个真实的例子：上一轮 orchestrator 提出「分段用 tier 而不是 prom，因为离散量更稳」，

如果当时只要求"讲得通"，那个错误前提百分之百会被采纳。

## 3. 不可以打破的东西

### 3.1 硬约束（用户环境决定，来自 req1.md）

1. **零外部依赖**。文件在 OneDrive 里，必须**离线双击就能打开**。
   不引 CDN、不引 Google Fonts、不装 npm、**不要 build step**。
2. **深色模式**跟随 `prefers-color-scheme`。
3. **颜色永远配图标 + 文字**，颜色不能单独承载语义。
4. 段 ①-⑤ 用同一条**单色相 5 级顺序色阶**；**⑥（中介）不在这条色阶上** ——
   它不是「更弱的 A」，是另一类东西，用中性灰 + 警示色 + 图标 + 文字。
5. `scripts/validate_palette.js` **在仓库里不存在**，别去找，也别为它造一个。

> v1 文档里的「零 JS」**不是硬约束**，是 v1 为了简单做的选择。
> 硬约束是「零外部依赖 + 离线可开」。R3/R4 可以写 JS，
> 只要是本地的、无依赖的、无构建的。

### 3.2 判定层不变量（破坏它们 = 把已修的 bug 装回去）

| # | 不变量 | 破坏后会怎样 | fixture |
|---|---|---|---|
| I1 | **零丢弃**：各段 raw 相加 == 窗口内去重后行数 | 岗位静默消失 | F12（目前按单日，R2 要改成按窗口） |
| I2 | **prom 只用于排序，绝不用于分段阈值** | prom 三遍一致率只有 84.6%，4.4% 的公司会跨阈值线；冻结进缓存 = 抖动永久固化 | 无，靠 review |
| I3 | **`stage < 1`（未富化）永不进 Lane C** | 富化晚一天，Amazon / Booz Allen / Micron 就进中介面板；空表时连 Deloitte 都进 | F6 / F8 / F18 |
| I4 | **所有「量」的判据用 7 天滑动窗口，绝不用累计** | 累计单调递增，约 10 天后 300 家公司全被误判成中介 | F5（背景流量 0→6000 行/天，命中数必须恒定） |
| I5 | **有自有 ATS board 的公司永不进中介段**（否决位，按行求值） | KAYAK、Jobgether 被误伤 | F4 / F7 |
| I6 | **应届相关性正则是分段依据，不是过滤器** —— 任何行都不许因为不匹配被删除，只是落到段 ③ | 破坏 I1 | F19 |
| I7 | **正则正文部分大小写不敏感，只有后缀标级 `\b(?:I\|1)$` 敏感** | 段① 从 28 行掉到 9 行 | F19 |
| I8 | **`daily_report.py` 一行都不许改** | 用户每天在看那个 md 日报，不能回退 | F17（逐字节比对） |
| I9 | **富化失败 / 无网 / 档案表缺失时 dashboard 仍能生成**，`profile()` 全函数永不抛异常 | 定时任务静默挂掉 | F8 |

### 3.3 首屏行数必须有上限，且上限不随采集量增长

`CAP = 2` 只约束单家公司，**不约束当天总量**。8/20 语料涨到 2072 行时，
段① 从 28 涨到 61 行、首屏涨到 73 行。所以加了 `OPEN_CAP`：默认展开的段各自截断到固定行数，
溢出的进嵌套折叠（**截断在排序上，不是在 prom 阈值上**，见 I2）。

**R2 会把这个问题放大 N 倍。** 机制可以直接沿用，数值要重新定 —— 见 4.2 决策 3。

## 4. 需求逐条展开

### 4.1 R1：趋势图天数

跟着全局的 N 选择器走。数据侧没难点，`per_day` 已经是按天聚合的。
注意 `days` 数组要包含**空天**（那天没抓到岗位也要占一个坑），否则柱子会挤在一起看不出断档。

### 4.2 R2：分段支持 N 天窗口 ★

当前 `day_rows(rows, day)` 做两件事：筛出 `_day == day`，然后按
**（公司, 归一化标题）** 去重。改成窗口后有五个决策：

**决策 1：去重必须在整个窗口上做，不能「每天各自去重再拼」**
`load_rows()` 已按 `unique_id` 全局去过一次，但**同一家公司在不同天发同名岗位**
会带着不同 `unique_id` 活下来（评审里 Deloitte 出现过 13 条同名岗位）。
按天去重再拼接 = 7 天视图里看到 7 条一模一样的 Deloitte「Software Engineer」。
→ 实现见 5.3 的去重键。

**决策 2：`CAP = 2` 在窗口下 = 「每家公司每段在整个窗口内最多先看 2 条」**
不是每天 2 条。否则 7 天视图里 Amazon 直接 14 行。

**决策 3：`OPEN_CAP` 数值要重定**
7 天窗口下段① 大约是单日的 5-7 倍，现在的 35 行会变成 200+。
**首屏目标仍然是 30-50 行**（用户在设计循环里明确认过的量级）。
建议不随 N 缩放 —— 无论看 1 天还是 30 天，首屏都是那 30-50 行最值得先看的，
其余在折叠里。

**决策 4：段内排序保持 prom 主序，但每行必须显示日期**
现在是 `(不在 priority 名单, -tier, -prom, -窗口内岗位数, 公司名)`。
用户是按公司质量挑岗位，所以 prom 主序不变；但 7 天的东西糊成一片会分不出新旧，
**日期列在窗口视图下是必需的**（单日视图下可以省略）。

**决策 5：窗口 ≠ 水位线，两者正交，不要合并**
- **窗口（N）** = 哪些行进入视野，用户主动选择的范围
- **水位线（`logs/last_report.json`）** = 这些行里哪些是「上次生成报告之后新增的」

7 天窗口里既有今天的新岗位，也有三天前就看过的。
**「● 新」必须继续由水位线驱动**，不能因为窗口是 7 天就把 7 天的都标成新的。
第 ⑦ 段（上一期未处理）在窗口视图下会和窗口内容大量重叠 ——
建议 N > 1 时把第 ⑦ 段**降级成一个筛选开关**（「只看上一期没处理的」），而不是独立一段。

### 4.3 R3：点击堆叠条 → 跳到对应分段

现状：HTML 里 `id=` 属性数量为 **0**。要做：

1. 每个 `<details>` 加 `id="seg-1a_t3"` 这类锚点
2. 堆叠条每个 `<rect>` 用 SVG 原生的 `<a href="#seg-1a_t3">` 包起来
3. 图例每一项同样可点
4. **`<details>` 被锚点定位到时不会自动展开** —— 需要十几行 JS：
   监听 `hashchange` + 首屏读 `location.hash`，`document.querySelector(hash).open = true`

第 1-3 步纯 HTML 零 JS，只有第 4 步要 JS。
另外加 `scroll-margin-top` 免得跳过去被顶部挡住，以及可见的 `:focus-visible` 样式。

### 5.2 数据结构

公司和行分开存，避免 tier/prom/公司名在每行重复（单日 1674 行只有 1127 家公司）：

```js
window.JOB_DATA = {
  generated:   "2026-08-21 08:00",
  cutoff:      "2026-08-21 00:24",   // 水位线，驱动「● 新」
  prev_cutoff: "2026-08-20 12:24",
  days: ["2026-08-15", ..., "2026-08-21"],   // 含空天

  companies: [
    {n:"Palantir Technologies", t:3, p:85, w:18, b:1},
    //  显示名                 tier prom  ↑     ↑ 有自有 board
    //                               7天滑动窗口内的岗位数（固定 7 天，见 5.4）
  ],

  rows: [
    {i:"4456201304",            // unique_id，行的稳定标识
     c:42,                      // companies 下标
     g:"1a_t3",                 // 段（Python 判定，JS 绝不重算）
     t:"Software Engineer, New Grad",
     l:"https://...",
     s:0,                       // 来源：0=newgrad 1=ats_direct 2=ddg
     d:"2026-08-20",            // 自然日
     r:"2026-08-20 12:24",      // 收录时刻，跟 cutoff 比出「● 新」
     k:"palantir\u0000software engineer new grad",   // 去重键，见 5.3
     sig:""},                   // 判定信号，展示用
  ],

  check: {"2026-08-20": {raw:1674, "1a_t3":70, "1a_t2":101, ...}}   // 见 5.6
}
```

实测大小：**每行 152 字节**（已归一化、已去掉空格）。

### 5.3 ★ 分工线：判断留在 Python，取景交给 JS

**这是整个设计里最要紧的一条。**

| | 谁做 | 为什么 |
|---|---|---|
| 行属于哪个段（`g`） | **Python** | 分段判据牵着 I2/I3/I5/I6/I7 五条不变量，全都有 fixture 守着。**JS 绝对不许自己重算** |
| tier / prom / 中介判定 / 信号 | **Python** | 同上 |
| **去重键（`k`）** | **Python 预生成** | 见下 |
| 按 N 天筛选 | JS | 纯过滤 |
| 窗口内去重 | JS | 按 `k` 比字符串，不需要懂归一化规则 |
| cap-2、`OPEN_CAP` 截断 | JS | 纯计数，且依赖 N |
| 段内排序 | JS | 按 Python 给的 `p` 排，JS 不产生判断 |

**为什么去重键必须 Python 预生成**：窗口去重要按（公司, 归一化标题）判等
（`CL.norm` + `CL.tnorm`）。如果让 JS 重写一遍归一化，两边规则一旦漂移，
同一条岗位在 7 天视图里就会重复出现 —— 而这正是 R2 最容易出的错。
给 JS 一个现成的键，它就不可能算错。

### 5.4 ⚠ 陷阱：这里有两个「7 天」，不是同一个东西

- **判定窗口，固定 7 天**：判断「某公司刷屏」用的滑动窗口（不变量 **I4**）。
  这个**不能跟着用户选的 N 变** —— 它是检测逻辑的一部分，改了就等于改判据。
- **取景窗口，用户选的 N**：看哪几天的岗位。

数据里 `companies[].w` 永远是前者。用户把 N 调成 30 天，`w` 还是 7 天的数字，
表头也要照实写「7天」而不是「N天」。
**两者混在一起的话，N 一变，谁是中介就跟着变了。**

### 5.5 加载策略：按档分块，不要一次全塞

N 固定 5 档（1/3/7/14/30），所以数据可以**按天区间切块**，避免重复：

| 块 | 覆盖 | 估算大小（按 2000 行/天） |
|---|---|---|
| `d0` | 今天 | ~0.3 MB |
| `d1_2` | 前 1-2 天 | ~0.6 MB |
| `d3_6` | 前 3-6 天 | ~1.2 MB |
| `d7_13` | 前 7-13 天 | ~2.1 MB |
| `d14_29` | 前 14-29 天 | ~4.9 MB |

- 首屏只加载 `d0`（约 0.3 MB，秒开）
- 选 7 天 → 注入 `d1_2` + `d3_6` 两个 `<script>` 标签
- 选 30 天 → 再注入剩下两块
- **动态注入 `<script src>` 在 `file://` 下是可行的**（经典脚本不走 CORS），
  这是 fetch 之外唯一能按需加载本地数据的办法
- 磁盘总量约 9 MB 且**无重复**，比「每档各生成一个完整文件」（1+3+7+14+30=55 天份）
  省 6 倍，OneDrive 同步噪音也小得多

**折叠的段等 `<details>` 打开再渲染**（监听 `toggle` 事件）。
30 天视图一次性建几万个 `<tr>` 会卡死。

### 5.6 零丢弃怎么继续守住

这是渲染搬到 JS 之后唯一真正变弱的地方 —— I1 现在由 Python 的 fixture 守着，
搬走之后就落到没有测试框架的 JS 里了。做法：

1. Python 在 `check` 字段里写每天各段的行数（这些数字由现有 fixture 断言）
2. JS 渲染完，用自己算出来的计数跟 `check` 对账
3. 对不上就在页面顶部显示一条**红色横幅**，而不是静默少几行
4. 页面上继续显示 `raw 70 · cap2 61`（现在就是这么显示的），数字对不上肉眼能发现

## 6. ⚠ `file://` 的真实限制 —— 决定 R4 能怎么做

页面从 OneDrive **双击打开**，协议 `file://`，origin 是 `null`：

| 做法 | 能用吗 | 说明 |
|---|---|---|
| `<link rel="stylesheet" href="dashboard.css">` | ✅ | 同目录 CSS 正常加载 |
| `<script src="dashboard.js"></script>` | ✅ | **经典脚本**正常加载 |
| 动态注入 `<script src="data-xxx.js">` | ✅ | 5.5 的按需加载靠这个 |
| `<script type="module">` | ❌ | **ES 模块走 CORS，file:// 下直接被拦** |
| `fetch()` / `XMLHttpRequest` | ❌ | opaque origin，被 CORS 拦 |
| `window.JOB_DATA = {...}` 写在 `.js` 里 | ✅ | **喂数据的正确方式** |
| `localStorage` | ⚠ | **必须实测**。`file://` 的 origin 是 `null`，各浏览器行为不一致（有的把所有 `file://` 页面当同一 origin，有的直接禁用）。本轮只有「记住上次选的 N」这一处可选用途，读写都要 try/catch 且拿不到值时要能正常渲染 |
| 写本地文件（`showSaveFilePicker` 等） | ⚠ | 本轮用不到。将来做「已投/已忽略」时才需要验证 |
| npm / webpack / vite / TypeScript | ❌ | 违反「零依赖、无构建」 |

## 7. 已知的坑（都真踩过）

1. **`PYTHONIOENCODING` / `PYTHONUTF8`** —— `dashboard.py` 往 stdout 打印段号 `①`，
   控制台默认 cp1252 时直接 `UnicodeEncodeError`。`resolve_python.bat` 已统一设好，
   但在 bash 里手跑要自己 `export PYTHONIOENCODING=utf-8`。
2. **脚本目录里不能有名为 `queue.py` 的文件** —— 会 shadow 标准库 `queue`，
   `openai → httpcore → trio` 导入链直接炸。设计者和评估者各踩过一次。
3. **OneDrive 目录下写文件必须原子写**（临时文件 + `os.replace`），
   `company_lane.atomic_write_json()` 已封好。
4. **点值型断言会过期。** 语料每天在涨（8/20 从 1018 → 1674 → 2072）。
   **断言不变性和结构性质，不要断言具体数值。**
5. **不要用 `ats_registry.json` 当 `BOARD_COMPANIES`** —— 实测只多 2 家 3 行，
   用 `ats_jobs.csv ∪ ddg_jobs.csv` 里出现过的公司就够。
6. **两个采集器不能同时跑**（`ats_direct --expand` 和 `ddg_search --update-registry`
   都读-改-写 `ats_registry.json`，会静默丢更新）。跟 dashboard 无关，改调度时别踩。
